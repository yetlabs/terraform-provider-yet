# Action: yet_cloud_database_restore

Restores one of a database's copies in its place, on the copy's stage — or a BucketDB's version, from its history (`at`) — and waits for it to be back.

~> **Warning:** The database stops for a moment and starts again on the copy: what was written since is not in it. The file before is kept on its volume, `app.db.before-restore`, until the next restore. A BucketDB's version becomes its current one, its applications moving to it at their next transaction; what was written since stays in its history.

## Example Usage

```terraform
action "yet_cloud_database_restore" "ledger" {
  config {
    database_id = yet_cloud_database.ledger.id
    backup_id   = "bk_1"
  }
}

# Run it by hand, once the copy is the one — looked into in its Studio first:
#   terraform apply -invoke action.yet_cloud_database_restore.ledger

# A BucketDB's version, from its history — each commit its bucket keeps:
action "yet_cloud_database_restore" "orders" {
  config {
    database_id = yet_cloud_database.orders.id
    at          = "3/L4kqtJlcpXroDTDmJ+rmSpXd3dIbrHY"
  }
}
```

## Schema

### Required

- `database_id` (String) The database to restore.

### Optional

- `at` (String) A BucketDB's version, by its id in its history (`yet.Databases.Versions`). Not with `backup_id`.
- `backup_id` (String) The copy: one of its backups, or a file uploaded as one. Not with `at`.
- `environment_id` (String) The stage `at` is put back on, for an application's own BucketDB on several: its last unless set.
- `timeout` (Number) Up to how many minutes to wait: `10` unless set.
- `wait` (Boolean) Whether to wait for it to be back: `true` unless set.
